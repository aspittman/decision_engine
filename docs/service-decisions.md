This report describes the upgrade to the existing Decision Engine, audited against the current sibling MMonolith and CRM repositories on October 2, 2026. The code and isolated database verification are complete. Migration025 is applied to live CRM, and all five services completed live recommendation runs. Publishing the tested CRM monitoring endpoints remains pending GitHub write access. No purchases, outreach, applications, customer changes, or paid actions were performed.

1. **Existing Decision Engine architecture.** Python package, deterministic `StrategyEvaluation` strategies, generic weighted scoring and historical feedback, budget/dependency planner, tenant-scoped `Context`, CRM HTTP client/repository, older direct Supabase repository, and transactional PostgreSQL RPCs. Production CLI uses CRM. Existing modules cover domains, paid search, organic search, landing pages, outreach, client briefs, service-demand corroboration, and product-profile matching. Existing canonical service assessments were largely advisory entries in decision-run summaries rather than durable recommendations.

   Audit classification: ALREADY CORRECT: tenant filtering, immutable upstream intelligence, evidence foreign keys, deterministic legacy scoring, budget/dependency planning, transactional run persistence, approval/execution separation. PARTIALLY IMPLEMENTED: five-service assessments, source corroboration, profile matching, domain policies, correlation metadata. MISSING: service/decision dispatch, durable individual advisory recommendations, scoped active uniqueness, soft scores separated from matching, complete confidence/strategy/policy metadata. CONFLICTING: one active recommendation per type and triggers that rejected non-workflow advisory records. LEGACY: execution channel names and recommendation enums remain supported.

2. **Preserved functionality.** Existing strategies, scoring configuration, planner, transport retry/authentication rules, context validation, feedback service, execution capabilities, recommendation/review/evidence tables, and old run behavior remain. Default organization runs now append canonical advisory decisions for enabled services. Explicit service requests use the new framework alone. All pre-existing uncommitted work was retained. No MMonolith code or research collectors were modified.

3. **MMonolith architecture discovered.** `services/domain_merchant` delegates domain discovery/research to existing `domain_intelligence`; `devspace_services` produces attributed service-demand hypotheses; `devspace_clients` discovers customer/referral prospects and performs bounded HTTP audits; investor and scholarship pipelines share `services/shared/product_research.py`. Publication uses the existing outbox, `ClientResearchSupabase`, and `loop_publish` contract. Source collection, quotation verification, discovery, and history observation remain MMonolith responsibilities.

4. **Exact intelligence contracts consumed.** All reports require the requested tenant, `status=CURRENT`, explicit `is_test=false`, and a report timestamp within configured signal age (default 30 days). Latest report per subject wins. Canonical metadata service identity is required except existing domain reports, which legitimately omit it.

7. **Supported decision types.** Domain: RESEARCH_DOMAIN, ACQUIRE_DOMAIN, PRICE_DOMAIN, START_OUTREACH, CONTINUE_OUTREACH, STOP_OUTREACH. Services: RESEARCH_SERVICE, TEST_SERVICE, OFFER_SERVICE, CONTINUE_SERVICE, RETIRE_SERVICE. Clients: IDENTIFY_OPPORTUNITY, RECOMMEND_SERVICE, PRIORITIZE_WORK. Scholarship: CHECK_ELIGIBILITY, MATCH_SCHOLARSHIP, RANK_OPPORTUNITY. Investor: CHECK_COMPATIBILITY, MATCH_INVESTOR, RANK_INVESTOR. Defaults: ACQUIRE_DOMAIN, TEST_SERVICE, IDENTIFY_OPPORTUNITY, MATCH_SCHOLARSHIP, MATCH_INVESTOR. Decisions within a service share policy where appropriate. Ranking requests order by descending score, confidence, then stable subject ID; eligibility checks expose the same individual mandatory rules.

8. **Domain logic.** Reuse existing transparent domain score. ACQUIRE requires every acquisition check plus minimum score and minimum confidence. Known conflict, over-cap price, geographic mismatch, negative sufficient-sample feedback or channel policy blocks produce DO_NOT_ACQUIRE. Missing/unverified evidence produces RESEARCH_FURTHER. RESEARCH_DOMAIN remains investigative. PRICE_DOMAIN returns observed comparable statistics for review and never an invented listing valuation. Outreach reuses scoped, report-linked buyer-fit/contact/permission/ownership signals. Sufficient negative response history recommends STOP_OUTREACH; other outreach requests require the existing outreach assessment to reach REVIEW, otherwise NEEDS_INFORMATION.

9. **Service logic.** Only SERVICE opportunities with fresh referenced observations are evaluated. Reuse independent-platform corroboration, ignoring supply listings/search snippets and deduplicating syndicated confirmations. TEST_SERVICE requires direct buyer requests, at least two independent platforms, affirmative delivery capability, known unit economics, adequate score/confidence. Explicit inability produces DO_NOT_TEST. A promising opportunity leads to a bounded experiment, not a business pivot. OFFER/CONTINUE/RETIRE return REVIEW_OUTCOMES when recorded outcomes exist, otherwise NEEDS_INFORMATION: existing outcomes do not establish causality, profitability or an approved commercial rollout.

10. **Client logic.** Use actual source/finding timestamps and references. HTTP 500–599 findings recommend REVIEW_WEBSITE_AVAILABILITY with HIGH priority, not an asserted root cause. Sourced prospect-fit REVIEW findings can recommend REVIEW_CLIENT_OPPORTUNITY. RECOMMEND_SERVICE without a supported technical finding returns NEEDS_INFORMATION. Minor findings receive lower scores/priority; absent evidence creates no recommendation. Performance optimization/SEO/automation recommendations cannot be fabricated from the current HTTP-only audit.

11. **Scholarship logic.** Fresh verified issuer page, reviewed normalization, individual mandatory comparisons, complete requirements, current availability and known fixed/rolling deadline are required for confirmed eligibility. Numeric rules accept only finite numbers; case-insensitive normalized string equality/membership are deterministic. A clearly failing requirement is INELIGIBLE; missing fields are NEEDS_INFORMATION. Expiration blocks applying; source conflict or unverifiable/stale sources remain unknown. Confirmed eligibility recommends APPLY subject to human review, independently of the soft score. Strong soft matches require score≥70 and weighted soft coverage≥0.8. Existing country/state/major/education_level profile aliases are retained.

12. **Investor logic.** Apply sourced criteria to the supplied business profile. Confirmed compatibility additionally requires explicit industry, stage, geography (country or region), both check-size bounds, funding amount and matching currency. Missing check-size evidence stays unknown. Known failed mandatory criteria produce INCOMPATIBLE regardless of soft attractiveness. Compatible businesses receive REVIEW_FOR_OUTREACH, never a contact action. Activity/portfolio evidence describes investors; it does not imply investor interest or portfolio similarity.

13. **Exact formulas/weights.** Missing dimensions contribute zero points and lower evidence coverage; they are identified as missing, not asserted to have measured value zero.

   * Domain: `clamp(sum(weight × normalized_factor) − penalties,0,100)`. Default weights: demand20, commercial_intent20, comparable_sales15, buyer_density15, historical_performance15, trend10, brandability5. Demand=min(1,max search volume/1000); comps=min(1,count/3); buyers=min(1,count/3). Optional metrics require 0–100 values, fresh observation dates and source references; factor=value/100. Penalties: trademark100, above acquisition cap20, weak buyer pool15, poor sufficient-sample outreach15. Existing configuration overrides domain weights/normalizers after validation.
   * Services: demand25, independent confirmation20, economics15, capability25, recurring10, accessibility5. Demand=`research_score/100`, where research_score=min(100,min(25,requests×5)+min(60,independent platforms×15)+min(15,support kinds×5)). Confirmation=min(1,platforms/3). Economics=min(1,(price/hours)/100); capability/recurring are explicit booleans; accessibility=share of direct requests containing a buyer record. There is no invented competition score; current observed supply counts do not establish competitive intensity.
   * Clients: 80 for observed HTTP server failure; otherwise min(60,fit_score×0.6). This is diagnostic/review priority, not expected customer value.
   * Scholarship: award60×min(1,award_min/5000), only with matching declared currency; time40×clamp(days before deadline/30,0,1). Unknown award/time does not affect mandatory eligibility.
   * Investor: activity50×(active=1,inactive=0,other labels unknown); recent investment30×max(0,1−age_days/365), future dates excluded; portfolio evidence20×min(1,verified portfolio count/5). Portfolio count measures documentation, not similarity or interest.

14. **Exact hard policies.** Domain: fresh sourced CLEAR trademark screening (observed_at within30 days), ≥3 comps, ≥100 monthly searches, ≥1 observed buyer and fresh buyer evidence, quote checked within24 hours, availability `available`, provider GoDaddy, checkout_total price, matching currency, positive price≤configured domain cap, geographic subset of target locations, no sufficient-sample negative-response imbalance, no blocked ACQUIRE_DOMAIN/DOMAIN_ACQUISITION/domain_merchant channel or saturation. Score default≥50; confidence≥organization minimum (default0.65). Unknown trademark clearance never qualifies acquisition. Outreach gates: domain_owned/outreach_authorized/contact_permission must be measured100; buyer_fit/contact_quality/offer_relevance required. Services: affirmative `delivery.can_deliver`, known positive hours/price economics, direct requests and ≥2 platforms, score/confidence thresholds. Client rules do not infer service scope from prospect fit. Products: freshness≤30 days, verified issuer, reviewed normalization, complete requirements/mandate, currently accepting applications/investments; mandatory criteria never hidden in a soft score. Investor dimension/check/currency requirements above apply. No strategy grants execution.

15. **Score versus confidence.** Score is opportunity/review attractiveness in [0,100]. Confidence is evidence certainty in [0,1]. Domain confidence=report confidence×measured-weight coverage. Services confidence=report confidence×factor coverage×min(1,independent platforms/3)×min(1,linked observations/5). Clients confidence=min(report confidence,individual fit confidence); HTTP findings do not manufacture extra fit certainty. Products confidence=report confidence×known-rule fraction×`rule_count/(rule_count+missing_information_count)`; unverifiable/conflicting/stale opportunities have confidence0. Strong opportunity with confidence0.1 remains distinct and does not satisfy acquisition/test thresholds.

16. **Historical outcomes.** Preserve existing pooled CPL/ROI feedback, shrunk toward neutral with n/(n+configured prior samples), tenant/subject/currency scoped. New domain scores retain the existing negative-response penalty only at ≥30 sent observations and use the same minimum to recommend stopping outreach. Other service histories are referenced as observations with score_adjustment0. Missing histories are INSUFFICIENT_DATA, not automatic rejection. Outcome presence alone does not justify offering/retiring a service. No weights are automatically changed. MMonolith does not currently expose a typed strategy-adjustment proposal contract; automated proposal generation is deferred until suggested changes and supporting sample lineage are available.

17. **Evidence lineage.** Every advisory recommendation has an INTELLIGENCE_REPORT evidence row and a versioned RULE row. Outreach additionally includes referenced MARKET_SIGNAL rows. Structured candidate/source/quotation/criterion/fact/finding references remain in metadata.evidence_references. Internal IDs are retained exactly, alongside the parent report UUID. Existing recommendation_evidence tenant foreign keys and transaction validate durable links. Details include points, missing factors, hard checks, history references and business outcome.

18. **Workflow preservation.** Merge upstream metadata.workflow_context and authoritative top-level workflow/correlation/parent identifiers. Conflicting identities or tenant/service mismatches fail safely. Supplied context cannot replace different upstream identifiers. source_engine becomes decision_engine for the new record. Existing workflow_run_id/parent_run_id/correlation_id remain; no workflow ID is generated. Reports with correlation only retain that correlation. CRM validates real workflow ownership, canonical service, parent and correlation; its trigger populates service_id/workflow_run_id columns.

19. **Recommendation identity/persistence.** UUID4 created once per constructed row; existing CRM POST and de_finish_run persist the same ID atomically with evidence and run completion. Existing created_at/updated_at defaults remain authoritative. decision_run_id is the engine evaluation run, separate from upstream workflow_run_id. Existing active recommendation for the same service/decision/subject is returned in assessment references and suppresses a duplicate. The migration enforces concurrent uniqueness. POST writes are not blindly retried. More than100 advisory rows fail safely rather than silently truncating the CRM batch.

20. **Strategy versions.** Persisted in metadata.strategy_version: domain-acquisition-v2; domain-outreach-v1; other new evaluators v1. Recommendation explanation and RULE evidence retain versions and points. Future substantive changes must bump versions; existing records are not rewritten.

21. **Policy versions.** Domain acquisition now domain-acquisition-v3 because it requires sourced affirmative clearance; domain outreach domain-outreach-v1; other new policies v1. Policies remain deterministic. Default domain weights are unchanged. Configured policy/threshold data remains in snapshots/decision details, with explicit versions on the recommendation.

22. **Approval.** All new advisory records declare requires_approval=true and execution_authorized=false, execution_service=null, action_type=null. Human review can approve/reject the advice; modification requires a fresh decision. The queue excludes these advisory records, so approval itself does not create execution requests. Purchases, outreach, submissions, paid actions and customer changes need their own approved downstream action contract. Existing legacy executable recommendations still use existing CRM approval/capability/budget checks.

23. **Business rejection/system failure.** DO_NOT_ACQUIRE, DO_NOT_TEST, INELIGIBLE and INCOMPATIBLE are completed evaluations. `decision_runs.status=COMPLETED` and metadata.execution_status=COMPLETED are independent from metadata.recommendation/hard-rule status. Unknown evidence gives NO_EVIDENCE or NEEDS_INFORMATION. CRM failures, invalid data or persistence failures follow the existing failed-run path and never report fabricated persistence success.

24. **dsmonitor observability.** Existing reference-only context-read and post-success persistence receipts now carry canonical service, output recommendation UUID, input intelligence-report UUID, decision type, business recommendation, engine-run ID, preserved workflow and correlation. Events remain best effort; durable decision_runs, recommendations, recommendation_evidence and existing service_record_lineage are authoritative. No special monitor business decision logic was added. Handoff is deliberately absent for new advisory records because execution adapters/actions are null; existing executable flows continue separately.
